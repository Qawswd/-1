운영 환경: AWS Ubuntu 24/7 서버 + 휴대폰 Termux(SSH) + 텔레그램

## 0. 결론부터 — 숫자를 먼저 본다

| 항목 | 값 |
|---|---|
| 시드 | 400,000원 |
| 추가 입금 | 400,000원 × 5개월 + 700,000원 × 5개월 = 5,500,000원 |
| **총 투입 원금** | **5,900,000원** |
| 목표 | 100,000,000원 (10개월) |
| 필요 배수 | 원금 대비 **16.9배** |
| **필요 월 수익률(복리)** | **약 56%/월** (입금 시점 반영 계산) |

참고로 같은 입금 스케줄에서 월 10%면 10개월 뒤 약 854만원, 월 20%면 약 1,439만원, 월 30%여도 약 2,458만원이다.
세계 최상위 헤지펀드의 좋은 해가 **연** 30~40%다. 월 56%를 10개월 연속으로 내는 방법은 존재하지 않는다.

**대표이사로서의 결정:**

1. **1억은 KPI 가 아니다.** 1억을 KPI 로 잡는 순간 유일한 경로가 "20배 레버리지 올인 반복"이 되고, 그 경로의 10개월 내 계좌 소멸 확률은 사실상 100%다. 기준 파일의 GUARD·SAFE 가 반복하는 경고("격리 20배는 -4.7% 역행이면 증거금 전액 청산")가 그 뜻이다.
2. **우리 KPI 는 세 가지다.** ① 살아남는다(원금 590만원 보존) ② 검증된 기대값을 만든다(페이퍼 30건 이상, 수수료 반영 후 기대값 > 0) ③ 규율을 코드로 강제한다(사람이 어기고 싶어도 시스템이 막는다).
3. **현실적 목표 구간:** 기본 590만 → 700만(+19%), 잘되면 → 900만~1,200만(+50~100%). 이것도 월 5~10% 복리라 매우 공격적인 목표다. 이 구간을 10개월 동안 무너지지 않고 달성하면, 그때는 자본을 더 넣어도 되는 **검증된 시스템**을 갖게 된다. 그게 1억으로 가는 유일한 실제 경로다.
4. 오너(사용자)가 그래도 복권 시나리오를 원하면, **전체의 10%(월 4~7만원)만 "로또 슬리브"** 로 분리해 20배를 허용한다. 나머지 90%는 아래 철칙을 따른다. 로또 슬리브가 0 이 돼도 회사는 살아 있다.

## 2. 철칙 — 코드로 강제한다 (config.json `risk` + 이후 executor 하드코딩)

| 규칙 | 값 | 이유 |
|---|---|---|
| 1회 거래 허용 손실 | 계좌의 **1%** (검증 후 최대 2%) | 10연패해도 -10%. 20배 올인은 1패에 -100% |
| 레버리지 상한 | **5배** (로또 슬리브만 20배) | 20배: 4.7% 역행 = 청산. 하이닉스 무기한 15분봉 ATR 이 ~1.2%면 4 ATR 거리. 스파이크 한 번에 끝난다 |
| 최소 손익비 | **1.8** (기준 파일 기본 1.5보다 상향) | 승률 45%여도 기대값 양수가 되는 선 |
| 일일 손실 한도 | **-3%** → 그날 중단 | 연속 손실은 판단 오염을 부른다. 코드 잠금: `exchange.js` `HARD_LOSS_LIMITS`(최근 24시간·7일·30일 순손익, 설정은 더 낮추기만) |
| 주간 손실 한도 | **-6%** → 그 주 중단, 리뷰 | 2026-10-13 코드화(그 전엔 문서에만 있었다) |
| 월간 손실 한도 | **-10%** → 실전 중단, 페이퍼로 복귀 | 시스템이 고장났다는 신호. 2026-10-13 코드화 |
| 공격(attack) 모드 | 실전 판단에 **사용 금지** | 기준 파일 문서가 직접 "연출용, 동전던지기"라고 명시 |
| 확신도·기대값 | 확신도 = **익절이 손절보다 먼저 닿을 확률**. 주문은 **기대값(확신도×손익비 − (1−확신도)) ≥ +0.2R** 일 때만 (손익비 1.8이면 확신도 43% 이상). 코드 잠금: `exchange.js` `HARD_MIN_EV_R` | 2026-09-30 개정(구: 확신도 65%). 캘리브레이션 결과로 올릴 수만 있음 |
| 수수료 | 판정 전 반영 | 20배에서 테이커 왕복(0.05%×2)은 **증거금의 2%**. 스캘핑 목표가 이걸 못 넘으면 수학적으로 손실 |
| 관망 | HOLD/PASS 는 정상 결과 | "안 하는 것"이 가장 흔한 최선의 결정이다 |

### Phase 1 — 데모 자동매매 + 백테스트 (D+3 ~ D+30) · 실제 돈 0원
- **1차 프로젝트가 이미 여기까지 만들어 놨다** — 데모 계좌 체결 3건(+66.49 / −10.70 / −6.42 USDT). 표본이 없을 뿐이다
- [x] **백테스터 완성·실행** (`server/backtest/`, `docs/04-BACKTEST.md`). 결과: **감시 트리거 자리 자체에는 우위가 없다** (BTC PF 1.05, ETH 음수, 채택 기준 통과 0건). 유일한 포켓 H1 "BTC 2% 급락 + 20일 저점권 → 롱" 은 n=104 의 가설. 숏은 전 구간 근거 없음
- **따라서 실전 진입 조건에 추가:** AI 판정 집합이 같은 기간 기계 규칙(H1·H2)보다 나아야 한다. AI 가 동전던지기 위에서 우위를 못 만들면 AI 를 쓸 이유가 없다
- **다음(대표이사):** 감시기가 트리거마다 H1/H2 기계 판정을 후보 로그에 같이 기록하게 해서 데모 기간에 AI vs 기계를 나란히 비교. 영상 전략도 같은 틀에 태운다
- 매일: 급변동 감시 → 자동분석(sonnet, 하루 8회 상한) → 데모 주문. 판정·체결·비용 전부 자동 기록
- **표본 속도(2026-09-28 결정):** 15분 ±1.5% 트리거는 BTC 기준 한 달에 3~6일, 조용한 달엔 0일이라 트리거만 기다리면 30건에 반년이 걸린다. 그래서 `schedule` 로 **하루 2회 정기 분석(BTC 09:10 · ETH 22:10 KST)** 을 추가해 AI 판정 표본을 모은다. 이건 수익 장치가 아니라 관문 도달 속도를 위한 것. 트리거 기준은 낮추지 않는다(백테스트에서 1.0% 도 우위 없음, 한도만 태움). 정기 분석도 한도 소진(429) 중엔 자동으로 건너뛴다
- 일간 요약에 `감시 활동(24h)` 줄(급변동 트리거 수·예약 분석 수·BTC 15분 최대 변동)을 넣어 "조용한 날"이 고장인지 시장인지 바로 읽히게 한다
- **확신도 철칙을 코드로 잠금(2026-09-29):** 첫 정기 분석(BTC 09:19)에서 확신도 55% 매수가 데모 주문까지 나갔다. 철칙(65% 미만 진입 금지)이 문서에만 있고 코드에 없었다. `exchange.js` 에 `HARD_MIN_CONFIDENCE = 65` 를 두고 주문 직전에 막는다(설정으로 올릴 수만 있음). 판정 자체는 성적표에 그대로 남으므로 표본 수는 줄지 않는다. 이미 들어간 BTC 데모 포지션은 손절이 걸려 있어 그대로 둔다
- **확신도 재정의 + 기대값 게이트(2026-09-30, 위 65% 잠금을 대체):** 정기 분석 4건의 확신도가 전부 55~58% 였다. 원인은 AI 지시문에 확신도 정의가 없었던 것("0~100 정수"뿐)이라 애매할 때 55~60 을 습관적으로 썼다. 또 손익비 1.8 에 확신도 65% 를 동시에 요구하면 1회 기대값 +0.82R 짜리만 들어가는 셈이라 사실상 주문이 나가지 않는다(본전 승률은 36%). 결정: ① 확신도를 "익절이 손절보다 먼저 닿을 확률"로 모든 최종 판정 지시문에 정의 ② 주문 조건을 기대값 ≥ +0.2R 로 교체(코드 하한, 설정으로 올리기만 가능) ③ 성적표에 확신도 구간별 "말한 확률 vs 실제 익절 비율" 캘리브레이션 표 추가. AI 의 확률이 과대평가로 나오면 30건 시점에 기준을 올리거나 확신도를 빼고 손익비만 쓴다. 기존 4건은 정의 전 표본이라 캘리브레이션 해석 시 따로 본다

- **안건 ⑧ 처리 — 주·월 손실 한도가 코드에 없었다(2026-10-13):** 계획서 철칙 일 −3% · 주 −6% · 월 −10% 중 코드에는 하루 한도만 있었고, 그마저 설정을 0 으로 바꾸면 꺼졌다(서버 기본값은 5%). 또 AI 가 포지션 전환을 고르면 기존 포지션을 먼저 청산한 뒤에 손실 한도를 봐서, 한도에 걸리면 '청산만' 하고 새 진입은 못 하는 순서였다. **결정·조치:** `exchange.js` `HARD_LOSS_LIMITS` 로 세 한도를 코드에 잠갔다 — 최근 24시간·7일·30일 순손익(실현손익+수수료+펀딩, 거래소 기록)이 계좌(`accountSizeUsd`)의 3·6·10% 손실이면 신규 진입을 멈추고 텔레그램으로 알린다. 설정은 더 낮추기만 되고 0 이면 철칙값. 굴러가는 창이라 손실이 창 밖으로 지나가면 자동으로 풀린다(오너 조작 불필요). 손실 한도·연속 손실 점검을 포지션 전환 청산보다 앞으로 옮겼다. 열린 포지션은 계속 거래소 손절이 보호한다. 판정은 성적표에 그대로 기록되므로 표본은 줄지 않는다. 남은 ⑧ 항목: 숏 차단 게이트는 국면별 숏 성적을 보고 결정, '누적 손실 10% 정지'는 월 −10% 로 대신한다, 하루 2% 하향은 Phase 2a 전환 때 300 USDT 기준으로 다시 본다
- **데모 거래소는 실제 시장과 다르다(2026-10-08 확인, `ops/demo-vs-real.js`):** 평소 마크가 차이는 0.01% 수준이지만 10/7 급락 때 BTC 1분봉이 실제보다 0.9~1.7% 높았고, 10/6 BTC 펀딩비는 실제 −0.0025% 대 데모 +0.20~0.28%(8시간당). 10/7 BTC 롱은 데모 84,884 에 정리돼 +4.60 이었지만 같은 시각 실제는 83,640 — 실제였다면 약 −10 USDT. **결정:** 데모 계좌 손익은 참고용. Phase 2 관문의 낙폭은 실제 시세로 채점한 판정의 누적 R 로 잰다. 실제 체결 품질은 Phase 2a 소액 실전에서 잰다. 일간 요약에 참고용 표기
- **미국주식 무기한 후보 조사(2026-09-28):** 바이낸스에 TRADIFI_PERPETUAL 로 실제 상장·거래 중. 이력(일봉)은 TSLA 244일(2026-01-28~) · MSTR·COIN 232일(02-09~) · NVDA·META 187일(03-26~). SPXUSDT·HMSTR·FARTCOIN 은 주식이 아니라 밈코인. **결정: 지금은 넣지 않는다.** 이력이 6~8개월이라 백테스트는 겨우 가능한 수준이고, 한국 계정 거래 가능 여부는 미확인(하이닉스·삼성 전례). 추가 순서: BTC·ETH 관문 통과 → 데모 시험 주문으로 계정 제한 확인 → 이력 긴 순서(TSLA→MSTR·COIN) 백테스트 → 1종목씩
- 매주 일요일: `/stats` 성적표 리뷰 — 확신도 버킷별 실제 적중률(캘리브레이션), 손익비, 기대값
- 오너가 보내는 **영상 → 전략 규칙화 → 모듈로 구현 → 같은 페이퍼 장부에 태워 비교** (4절)
- **Phase 2 진입 조건 (전부 충족해야):** 실제 시세로 채점한 AI 판정 ≥ 30건(데모 체결 수가 아님) · 수수료 반영 기대값 > 0 · profit factor ≥ 1.3 · **실제 시세로 채점한 판정의 최대 낙폭 ≤ 15R**(매매당 1% 위험이면 계좌 15%) · **같은 기간 AI 판정이 기계 규칙(H1·H2, `docs/04-BACKTEST.md`)보다 우수** · **상승장 밖(횡보·하락) 판정 ≥ 8건이고 그 기대값 ≥ 0** · **같은 손절·익절 거리의 '무조건 롱'보다 기대값 우위** (2026-10-04 추가 — 상승장 덕과 판단력을 구분) · 실전 첫 달은 숏 금지 검토
- 조건 미달이면 Phase 1 연장. 입금은 계속하되 **현금으로 보관**한다. 검증 안 된 시스템에 돈을 넣지 않는 것이 이 달의 수익이다

### Phase 2a — 소액 실계좌 자동 주문 (Phase 1 관문 통과 후 4주)
- **오너는 주문하지 않는다(2026-10-05 오너 조건).** 오너는 폰을 상시 볼 수 없으므로 모든 주문·손절·청산은 AI·코드가 한다. 사람 손이 필요한 단계를 계획에 두지 않는다
- 목적은 수익이 아니라 **실제 체결과 데모의 괴리(슬리피지·체결 실패·수수료)** 측정
- **시작 금액은 위험 기준으로 정한다(2026-10-05):** 거래소 최소 주문(BTC 약 100 USDT·최소 수량 0.001 BTC로 알려짐 — 전환 시 exchangeInfo 로 실제 값 확인)으로 들어가도 1회 손실이 계좌의 1% 를 넘지 않아야 한다. 최근 판정 손절 폭 0.7~2.9% 기준 **실계좌 약 300 USDT** 로 시작(모은 원금 중 일부)
- 전환 전 준비물(전부 갖춘 뒤에만 `.env` 의 `BINANCE_FUTURES_BASE_URL` 을 실계좌로 바꾼다):
  - 오너 1회 작업: 실계좌 본인인증 · USDT 입금 · API 키 발급(**출금 권한 끔, 서버 IP 제한**) — 대표이사가 화면 단위로 안내
  - 코드: 텔레그램 긴급 정지(한 줄로 전량 청산·정지, 비상용) · 서버 무응답 감지 알림 · **최소 주문 기준 확인**(MIN_NOTIONAL·최소 수량 조회 → 미달이면 최소치로 올렸을 때 1회 손실이 한도 안일 때만 주문, 아니면 생략 알림. 위험을 넘기면서 키우지 않는다)
- 오너가 알림을 못 봐도 안전한 구조: 거래소에 미리 걸린 손절, 코드로 잠근 일·연속 손실·노출 한도 자동 정지, 30분 주기 무보호 포지션 복구·청산

### Phase 2b — 비중 확대 (2a 4주 성적이 데모와 비슷할 때)
- 매매당 위험을 철칙 1% 까지, 실전 투입은 누적 원금의 50% 까지 단계적으로 올린다. 나머지는 현금
- 2a 대비 성적이 무너지면 즉시 2a 크기로 되돌린다

### Phase 3 — 규모 확대 (검증된 뒤)
- 월 수익률·낙폭이 3개월 연속 기준 안이면 리스크 1% → 2%, 실전 비중 50% → 80%
- 이 단계에 도달하면 그때 "1억" 이야기를 다시 한다. 그 전에는 하지 않는다

## 4. 영상 분석 프로토콜 (오너가 영상을 보낼 때마다 적용)

1. **주장 분리:** 영상이 말하는 "전략(규칙)"과 "수익 주장(결과)"을 나눈다. 수익 주장은 검증 전까지 0 의 가치.
2. **규칙화:** 진입 조건 / 청산 조건 / 손절 / 비중 / 대상 자산 / 시간대를 숫자로 적는다. 숫자로 못 적으면 채택 불가.
3. **재현 가능성 판정:** 우리 데이터 소스(Binance·Yahoo)로 그 규칙을 계산할 수 있는가. 없으면 데이터부터.
4. **구현:** `server/` 에 모듈로 추가 → 에이전트 프롬프트 재료로 주입하거나 독립 신호로 페이퍼 장부에 기록.
5. **비교:** 같은 기간 같은 장부에서 기존 판정과 나란히 성적 비교. 이기는 쪽만 남긴다.
6. **채택 기준:** 페이퍼 30건 · 기대값 > 0 · 기존 대비 개선. 영상 속 "월 30%" 같은 숫자는 채택 근거가 아니다.

영상 하나당 산출물: `docs/videos/NN-<제목>.md` (규칙·판정·구현 여부·결과).

## 5. 거래소·법률 — 오너가 알고 결정할 것

- 기준 파일이 전제한 **탭비트(Tapbit)** 는 국내 미신고 해외 거래소다. 한국 거주자 대상 영업은 특금법상 신고 대상이라 이런 거래소는 **예치금 보호·분쟁 구제가 사실상 없다.** 출금 중단 리스크를 자본 손실 시나리오에 넣어야 한다.
- 같은 SKHYNIX-USDT 무기한이 **바이낸스·바이비트·비트겟** 에도 상장돼 있고, 기준 파일도 시세를 거기서 가져온다. 규모·유동성·API 성숙도 면에서 자동 주문 단계(Phase 2b)에서는 이쪽이 낫다.
- 국내 거래소(업비트·빗썸)는 레버리지가 없다. 대신 원화 입출금이 안전하다. 로또 슬리브가 아닌 90% 쪽 자금은 여기 두는 선택지도 있다.
- 세금: 가상자산 양도차익 과세 시행 여부·해외금융계좌 신고 기준은 매년 바뀐다. 실전 진입 전 그해 기준을 확인한다.
