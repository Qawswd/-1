## 근본 원인 4가지

### 1. 연료 — Claude 사용량 한도 (가장 큼)
- 알고리즘 모드 1회 = 에이전트 12~13명 × `opus`. 실패하면 각 에이전트가 **한 번 더 재시도** → 헛돈 호출 2배.
- 워치리스트가 미국주식 10종이라 트리거가 자주 왔고, 한도가 차면 **그 뒤 모든 런이 12명 전원 실패**로 기록됐다. 3일간 실패 런 160회 = 헛돈 호출 약 3,800번.
- 한도 메시지 `You've hit your session limit · resets 6:40pm (UTC)` 를 진단이 "JSON 형식 오류"로 오진해(674건) 09-22까지 한도 게이트가 작동하지 않았다.
- 09-22 이후에도 실패가 이어진 이유: 한도가 풀리자마자 opus 12명이 다시 5시간치를 태웠다. **모델과 호출 수를 안 줄이면 게이트만으론 못 막는다.**

### 2. 배포 — git 없이 tar 패치
- 파일을 폰에서 만들어 `scp` → 이름이 잘린 채 도착(`server/s`, `server/exch`, `~/tr`, `~/auth-1.js`, `test/agents.test.mj`) → 손으로 `mv` → 재시작. 이력에 이런 복구가 7번 있다.
- 무엇이 언제 바뀌었는지 추적 불가. 되돌리려면 `backup-before-*.tar.gz` 를 통째로 풀어야 했다.

### 3. 설정 — 조용히 틀어져 있던 것들
- 시간대 UTC → 예약·일간요약 시각이 9시간 어긋남. 스왑 0 → 2GB 인스턴스에서 여유 없음.
- 미국주식(V·NVDA·AAPL·META·WMT·QQQ·MSFT)은 **바이낸스에서 거래 자체가 안 되는데** 분석 한도만 소모했다. 09-24에야 BTC·ETH로 고정.
- `marketHoursOnly` 필터가 **암호화폐까지 미국 장중으로 제한**해 이틀간 분석이 0건이었다. 09-26에야 24시간 체제로.
- 포트 8000이 전 인터넷에 열려 있었다(로그인 페이지가 막아주긴 했다).

### 4. 증거 기근 — 배울 데이터가 안 쌓이는 구조
- 11일간 판정 42건 중 **HOLD 36건(86%)**. 방향 판정 6건, 데모 체결 3건. 이 속도면 통계가 나오기까지 **1년**이 걸린다.

## 이번엔 다르게 — 결정 사항

1. **서버 버전 코드를 새 기준으로 채택**하고 git 에 넣었다(이 저장소). 배포 = `git pull && npm test && systemctl restart`.
2. **자동분석은 `sonnet`**, 하루 상한 8회(`analysisBudget`), 실패 재시도 금지, 한도 게이트 문구 전부 인식.
3. 설치 스크립트가 **KST·스왑·.env·systemd** 를 고정한다. 손으로 만지는 설정은 `config.json` 하나.
4. **백테스터를 먼저 만든다.** 23.6만 봉 데이터로 감시 트리거 규칙(급변동+구조/역추세)을 Claude 호출 없이 몇 초 만에 검증한다. 영상에서 뽑은 규칙도 같은 틀에 태운다. 증거 기근을 여기서 끝낸다.
5. 실제 돈은 계속 0원. 데모 체결 30건 + 백테스트 근거가 갖춰지기 전엔 실계좌 URL 을 바꾸지 않는다.

### 2026-10-02 13:31 — 손절 재조정 실패로 BTC 데모 포지션 무방비

- **경위:** 13:29 BTC 15분 +1.53% 급변동 → 포지션 검토 AI 가 "이익 보호"로 롱 손절을 86,000 으로 올리라고 판단. 그 순간 현재가는 85,873 이라 롱 손절이 현재가보다 위 → 바이낸스가 `-2021 Order would immediately trigger` 로 거부. 그런데 코드는 **기존 손절(82,581)을 먼저 취소한 뒤** 새 손절을 냈기 때문에 포지션이 손절 없이 남았다. 무보호 점검은 재시작 때만 돌아 수 시간 방치.
- **원인:** `updateStopLoss` 가 ① 새 손절가가 현재가를 이미 넘었는지 확인하지 않았고 ② 제출 실패 시 기존 손절 복구·청산 없이 경고만 보냈다. 같은 파일의 진입 경로(손절 실패 → 즉시 청산)와 원칙이 달랐다.
- **조치:** 새 손절가가 현재가를 넘으면 아무것도 취소하지 않고 기존 손절 유지 → 제출 실패 시 기존 손절가로 즉시 복구 → 그것도 실패하면 시장가 청산 → 그것마저 실패할 때만 사람 호출. 무보호 포지션 점검을 30분마다 실행. 재시작 시 장부의 원래 손절가(82,581)로 자동 복원.
- **교훈:** 안전장치는 "정상 경로"뿐 아니라 "실패 경로"에서도 같은 철칙을 지켜야 한다. 데모라서 돈은 잃지 않았지만 실전이었다면 무손절 포지션이다.

### 2026-10-07 11:09~ — 트레일링 손절 계산 오류 + 같은 경고 약 180건

- **경위:** 11:02 ETH −2.23%·BTC −1.75% 급변동 → BTC 롱 청산(AI 검토), ETH 숏 신규 진입(2,630, 손절 2,687). 이후 트레일링이 숏 손절을 **1,689** 로 옮기려 함. 숏 손절은 현재가(약 2,617) 위여야 하므로 10/2 에 넣은 안전장치(즉시 체결될 손절은 적용하지 않고 기존 손절 유지)가 막았다. 기존 손절은 계속 걸려 있었다. 그러나 감시기가 1분마다 같은 계산을 반복하며 매번 알림을 보내 약 180건.
- **원인 1:** `highLowSince` 가 "진입 이후 봉"을 일봉 시작 시각으로 걸러, 당일 진입이면 해당 봉이 0개 → **전체 기간으로 대체**하는 설계였다. 몇 달 전 최저가 + 2.5 ATR = 1,689. 롱이었다면 역대 최고가가 들어가 같은 문제.
- **원인 2:** 포지션 검토·트레일링이 장부에서 "가장 최근 기록"을 실제 포지션으로 썼다. 09:16 BTC 매수 판정은 기존 롱 유지(KEEP)로 주문이 안 나갔는데 장부엔 남아, 11:04 청산 판단이 실제 포지션(진입 84,494)이 아니라 미체결 판정의 손절 84,700 을 근거로 삼았다(결과적으로 실제 손절 부근에서 정리돼 손익 차이는 작았다).
- **조치:** 진입 시각이 속한 봉을 포함하고, 진입 이후 봉이 없으면 계산하지 않음(대체 금지). 진입 시각을 덮으면 15분봉 사용. 장부 매칭을 "같은 종목·방향 중 거래소 진입가와 가장 가까운 기록"으로. 같은 트레일링 실패 알림은 6시간에 한 번, 제목을 "자동 트레일링"으로 구분. 회귀 테스트 3건.
- **교훈:** "데이터가 없으면 대신 다른 데이터로" 는 금지 — 지어내지 않는다 원칙과 같다. 10/2 의 실패 경로 안전장치가 실제로 손실을 막았다.

### 2026-10-08~09 — 트레일링이 손절을 느슨하게 되돌림(ETH 숏)

- **경위:** ETH 숏(진입 2,612.57)에서 트레일링 손절 제출이 `-1111 Precision` 으로 반복 거부. 10/2 의 복구 장치가 "기존 손절"로 되돌렸는데, 그 값을 장부(2,687)에서 읽었다. 그 사이 AI 포지션 검토가 실제 손절을 2,600 으로 당겨 둔 상태였으므로 **복구가 손절을 2,600 → 2,687 로 87달러 느슨하게** 만들었다(2,629 로 옮긴 뒤에도 같은 일). 같은 이유로 2,629 성공 알림이 10회 반복.
- **원인:** ① 트레일링·검토 경로가 손절가를 거래소 가격 단위로 맞추지 않음(진입 경로만 맞춤) ② 장부 갱신은 "같은 종목 최신 기록", 읽기는 "실제 포지션과 진입가가 가까운 기록"(10/7 수정)이라 서로 다른 기록 — 실제 포지션 기록의 손절이 옛값으로 남음 ③ 손절의 기준을 거래소가 아닌 장부로 삼음.
- **조치:** `updateStopLoss` 가 ① 가격 단위로 맞춤(롱 올림·숏 내림 = 느슨해지지 않는 쪽) ② 거래소에 실제로 걸린 손절을 조회해 **그보다 느슨하거나 같은 요청은 취소조차 하지 않고 거절** ③ 실패 복구도 실제 걸려 있던 값으로. 트레일링의 비교 기준도 거래소 손절. 장부 갱신은 읽은 기록(id)만. 거절은 알리지 않고, 실패 알림은 종목당 6시간 1회. 회귀 테스트 5건.
- **교훈:** 손절의 진실은 거래소에 있다. 장부는 사본이고 사본으로 보호 장치를 되돌리면 안 된다. 손절은 당기기만 한다 — 코드가 이를 강제한다.
